### Godot 4 踩坑（测试场景报错修复）
- **`SubViewport` 没有 `default_clear_color` 属性**（Godot 3→4 已移除；属性列表只剩 size / render_target_* / view_count）。给 SubViewport 设背景色要用 `WorldEnvironment`(Environment, background_mode=Environment.BG_COLOR, background_color=...) 放在视口内，或 `transparent_bg=true`+外层 ColorRect。
- **GDScript 4 的 `/` 恒为浮点除法**：`var row := i / 2` 得 0.0/0.5/1.0/1.5，2×2 网格第二块会错位 → 用 `int(i / 2)`。
- **字典取值是 `Variant`**：`info["bg"]` 直接赋给 `Color` 属性会报「Cannot assign Variant to Color」→ 用 `as Color` 转型。

## 监控屏「白板」二次根因 + 修复（用户反馈：转180后上面没画面=白板）

用户：「你屏幕搞反了，我给你转了180，然后上面没画面，游戏时，那玩意就是白板」。

### 诊断偏差纠正
- 我之前的认知偏差：**BoxMesh 是 6 面都贴图的**（UV 都映射到整个 texture 空间 0~1），**不存在「只有一面有画面」**。白板不是「背面没贴图」。
- 真正原因：**SubViewport feed 没渲染出有效内容 + BoxMesh 材质 `emission_enabled=true emission=Color(1,1,1,1)`（默认 albedo 也是白色）**。空 viewport + emission 白光 + albedo 白覆盖 = 视觉上的「白板」。
- 触发条件三重叠加：① `render_target_update_mode = 1 (UPDATE_ONCE)` 在 FeedTimer 重设时不一定可靠触发新帧；② `FeedCam.current = false`，SubViewport 不一定会用它做相机；③ 屏幕材质没有任何兜底深色，未渲染时就是白光。
- MonitorPanel 朝向：用户转的 180° 实际是修对了朝玩家方向（X 轴 (-1,0,0) = 已翻转），现在 Z 法线 ≈ (0, 0.276, -0.961) 朝玩家 -Z，**朝向本身没问题**——所以原计划「每块屏幕加 rotation.y=PI」是错的（会反而把画面翻出去），已撤回。

### 修复（已 MCP 验证 errors:[]）
- `bridge_whitebox.tscn`：4 个 SubViewport → `render_target_update_mode = 2 (UPDATE_ALWAYS)`；4 个 FeedCam 加 `current = true`；4 个屏幕材质加 `albedo_color = Color(0.05, 0.06, 0.08, 1)`（黑屏时是深色，不会被白光糊成白板）。
- `bridge_whitebox.gd`：`_on_feed_timer` 改成 noop（持续模式不需要 timer 驱动 viewport；保留函数体作为未来切回 UPDATE_ONCE 时的开关位）。

### 第三次根因：SubViewport 未共享主世界（2026-09-01 16:14 用户反馈后定位）
- 用户发现：① 屏幕确实没画面；② 4 个监控相机全部留在原点、朝向一致，没有被 `_aim_feeds()` 移动/转向。
- 探索 agent 定位：`SubViewport` 默认 `own_world_3d=true`，每个 SubViewport 拥有独立 `World3D`，里面只有自己的 `FeedCam`，没有主世界的标记物、灯光、环境。
- 后果：feed 相机拍的是空世界 → 屏幕无内容 → 被白光覆盖成白板；空世界里没有参照物，所以看起来相机「没动」。
- **修复**：在 `bridge_whitebox.gd` 的 `_ready()` 中、`_aim_feeds()` 之前，显式让 4 个 SubViewport 共享主世界：
  ```gdscript
  var main_world := get_viewport().world_3d
  for sv in _feeds:
      sv.world_3d = main_world
  ```
- 已加清晰注释说明原因（按用户要求：每个代码板块都要注释清楚功能）。
- MCP 验证：`errors: []`，尺度自检 4 条全 OK。待用户 F5 验证 4 屏是否显示蓝/绿/橙/紫四向彩色标记。

### 用户元反馈（已执行）
- 用户要求：「以后代码每个板块实现的功能，要有清楚注释，帮自己也帮我方便搞清楚代码到底对不对」。
- 已在本次修复处加明确中文注释，解释 SubViewport 必须共享主世界的原因。

### 教训（已记 MEMORY.md）
- 用户反馈「转 180° 后还是反的」时，先验证目标 mesh 是否单面贴图，不要直接假定「背面没画面」。**BoxMesh/QuadMesh/SphereMesh 都是各面共享整张 texture**，单面贴图只对 PlaneMesh / 自己写的 Quad/带背面剔除的 PlaneMesh 等少数情况成立。

- 核心架构一致（SubViewport+Camera3D+ViewportTexture+UPDATE_ALWAYS），但文档用 **TextureRect(2D UI)** 显示，我用 **3D 网格屏**；文档让"在检查器设 Viewport Path"——**正是之前 `Path to node is invalid` 的写法**；文档**漏了 world_3d 共享**（我们踩的第二坑）。结论：是概念入门文，不是我们 3D 物理屏场景的施工手册。

### 关键诊断：摄像机其实已被脚本移到舷外四向
- MCP 重跑 `[aim]` 打印 + `[diag]` 四屏中心像素=蓝/绿/橙/紫**四种不同色** → 证明 4 相机在 4 个不同位置、拍到各自不同标记，**根本不在原点**。

### 本轮双保险加固（已 MCP 验证 errors:[]）
1. **把 4 个 FeedCam 的 position+rotation 直接写进 `.tscn`**（用 `look_at` 反算的 Transform3D：port 看 -X / stbd 看 +X / dorsal 看 +Y / ventral 看 -Y），编辑器里就能看到相机已摆好；脚本 `_aim_feeds()` 保留作兜底（`.tscn` 被编辑器回退时运行时照样移）。

## 第 09 课：打磨游戏的操作反馈（Game Feel / Juiciness）

### 核心命题
从「能玩」到「好玩」的最后一公里。不是单一功能，而是十几个细节叠加起来的感觉。

### 元原则（第零步）：让 AI 自己决定「放在哪」
你负责说"想要什么效果"，AI 负责说"放到哪、怎么连"。

**元提示词模板**：
```markdown
背景：
- 引擎：____（Godot 4 / Unity 2D）
- 项目当前结构：请先列出我现有的脚本目录、autoload/单例
- 已有的反馈相关代码：____
- 我想做的事：_____（如"命中钉子画面停半秒再缓动"）

请按以下顺序回答（不要写代码）：
1. 最干净的实现放在哪个脚本/节点？为什么？
2. 现有代码能复用吗？（信号/硬件/接口）
3. 需要暴露哪几个数值到编辑器？给我"通常合理的范围"
4. 有没有这个引擎专属的、新手容易踩坑的写法？
```

### 关键认知转变
**不要第一次就让 AI 给"带数值的参数表"**——它的初值几乎都不对（它给的是同品类在线游戏的均值）。先让它给「有哪些旋钮」，旋钮转到几留到引擎里自己调。

### 手感清单 Prompt
```markdown
背景：这是我的弹珠肉鸽游戏。
我录了一段 30 秒的玩法流程（或口头描述）。

任务：从「手感 / Juiciness」角度列出缺失或薄弱的反馈点。

约束：
1. 不要写代码，不要给具体参数数值
2. 按「输入反馈 / 命中反馈 / 镜头反馈 / 音频反馈 / UI 反馈」五类分别列
3. 每类说清"现在是什么、期望变成什么、为什么"
4. 优先排序：哪些是「不加就难受」，哪些是「锦上添花」
5. 列完后问"要不要先开始补？"
```

> ⚠️ mp4 无法直接发给 AI，需要先转 GIF。

### 反馈管线（本课做前 5 条，一次只做一层）

| 序号 | 反馈层 | 效果 | 优先级 |
|------|--------|------|--------|
| ① | **Hitstop（命中冻结）** | 命中瞬间画面暂停几十毫秒 | ★ |
| ② | **命中闪白** | 被击中物体瞬间变亮再还原 | ★ |
| ③ | **屏幕震动 Shake** | 钉子碎裂时画面微震 | ★★ |
| ④ | **Zoom Punch（拉镜）** | 关键时刻画面短暂"凑近"再回弹 | ★★ |
| ⑤ | **浮动伤害数字** | 命中点蹦出数字飘出淡出 | ★★ |

后续可补：粒子（钉子炸裂）、拖尾、UI 心跳缩放、命中减速、连击 BGM 加层。

### Hitstop 实现要点（Godot 4）
`Engine.time_scale = 0` 的副作用排查：
1. **RigidBody2D 物理** → 也会暂停（这是我们想要的）
2. **AudioStreamPlayer** → 也会暂停（击球音不能被打断！）
3. **AnimationPlayer** → 也会暂停
4. **Timer 节点** → 也会暂停（HUD 倒计时不受影响？不，也会停）

**因此用 `time_scale` 做 Hitstop 有副作用**——需要更精细的方案（如自定义 hitstop 计时器，只冻结物理和渲染，保持音频和 HUD 计时器运行）。

目标：时长暴露为编辑器可调参数，范围 **0.025 ~ 0.2s**

### 铁律
> **一次只做一层，做完自测 1 分钟，再做下一层。**
> 一次做 5 层 = 5 个脚本互相踩 = 同时引入 5 个 bug。

### 引擎副作用检查 Prompt（做完一层后补上）
```markdown
你打的 Camera 单震，在 Godot 4 里会同时影响哪些正在运行的东西？
请列举：UI 动画、Timer、粒子、音效等，告诉我哪些受影响，哪些不受影响。
```

## 第 10 课：为游戏注入听觉体验

### 核心理念
> **声音不是"做完再加"的装饰，而是手感（juicy）的一半。**
> 免费资产三层级：免费库（freesound）→ AI 生成（Suno）→ 自己录

### 声音分层架构
```
Master
├── Music（BGM 总线，-6dB）
├── SFX（Gameplay 音效）
│   ├── sfx_peg_hit
│   ├── sfx_bucket_normal / reward
│   ├── sfx_ball_launch
│   └── sfx_ballcount_up / down
└── UI（界面音效）
    ├── ui_button_hover
    ├── ui_button_click
    └── ui_settle_popup / ui_panel_*
```

### 完整声音清单

#### SFX-Gameplay
| 英文事件名 | 触发时机 |
|-----------|---------|
| sfx_peg_hit | 弹珠碰撞图钉 |
| sfx_bucket_reward | 弹珠落入奖励袋洞 |
| sfx_bucket_normal | 弹珠落入普通袋洞 |
| sfx_ball_launch | 发射弹珠 |
| sfx_ballcount_up | 球数 +N |
| sfx_ballcount_down | 球数 -N |

#### SFX-UI
| 英文事件名 | 触发时机 |
|-----------|---------|
| ui_button_hover | 鼠标悬停按钮 |
| ui_button_click | 点击按钮 |
| ui_settle_popup | 结算弹窗弹出 |
| ui_panel_promote | 晋级面板显示 |
| ui_panel_fail | 失败面板显示 |
| ui_countdown_warning | 倒计时最后 10 秒 |
| ui_countdown_zero | 倒计时归零 |

#### BGM
| 轨道 | 场景 | 循环 |
|------|------|------|
| bgm_main_menu | 主菜单 | 是 |
| bgm_gameplay | 对局进行中 | 是 |
| bgm_shop | 商店界面 | 是 |
| bgm_boss | Boss 关卡 | 是 |
| bgm_defeat | 失败结算 | 否（单次） |

### 高频音效防爆策略
1. **时间窗口限流**：50ms 内同类 sfx_peg_hit 最多触发 2 次，超出丢弃
2. **实例复用池**：2~3 个 AudioStreamPlayer 轮转，超过容量丢弃
3. **同帧去重**：同一 physics frame 内同一颗球碰多个图钉，只发一次（取最先碰撞的）

### 音高变化策略
| 弹珠速度 | pitch_scale | 听感 |
|---------|------------|------|
| 200–500 | 1.0 | 原音高 |
| >500 | 1.26 | 高 4 个半音（升大三度） |

低速碰撞低沉浑厚，高速碰撞尖锐清脆——玩家仅凭声音就能判断速度。

### BGM 切换交叉淡化
- 旧 BGM：**0.8s 线性淡出** 至 -60dB 后停止
- 新 BGM：旧 BGM 开始淡出 **0.3s 后**启动，**0.5s 线性淡入**至 -6dB
- 总切换时间：0.8s

### AudioManager 架构
**采用 autoload 单例**（与 GameManager 同级），理由：
1. 全局访问：音效散布在场景树各处（peg/bucket/launcher/HUD）
2. 总线集中管理：三条总线的创建、电平、静音、音量滑块
3. 跨场景持久性：BGM 在场景切换时不中断
4. 与现有架构一致：GameManager 已是 autoload，两者通过信号通信

### API 签名（参考）
```gdscript
AudioManager.play_sfx("sfx_peg_hit")
AudioManager.play_sfx("sfx_ball_hit", ball_speed)
AudioManager.play_sfx("sfx_ui_click")
AudioManager.play_bgm("bgm_xxx")
```

### 音频配置：不 hardcode preload
- 音频路径写在 `audio_config.json`
- 缺失时只 warn，不影响运行
- 不要写 `preload()`，Godot 启动时找不到文件会直接报错

### 第 1 轮 Prompt（列清单）
```markdown
列出本游戏所有需要发声的事件，按 SFX-Gameplay / SFX-UI / BGM 三类归口：
1. 每个事件给一个英文事件名 (如 sfx_peg_hit) 和一句触发时机
2. 对于"钉子碰撞"这种高频音效，列出防溅和音高变化策略
3. 对于 BGM，列出本游戏总共会出现几条 BGM 轨道？每条在什么场景播放？切换之间需要淡入淡出几秒？
4. 你打算把音频系统做成 autoload 单例还是节点挂载？请说明理由

不要写代码，只给出文字描述。
```

## 第 11 课：与朋友进行第一次测试

### MVP 核心循环验证
| 规则 | 数值 |
|------|------|
| 起始球数 | 50 |
| 一局倒计时 | 90 秒 |
| 晋级阈值 | 球数 ≥ 60 |
| 失败条件 | 倒计时归零且 < 60 |
| 奖励袋洞 | 球数 +3 |
| 普通区域 | 球数 -1 |
| 手动结算 | 随时可点 |

### 翻 Bible
| 你要改什么 | 读哪个文件 |
|-----------|-----------|
| 加新实体 | 02_entities.md |
| 调数值 | 03_rules.md |
| 改 UI/HUD | 05_ui_hud.md |
| 加新模块/调目录 | 07_file_layout.md |

### 三轮对话节奏

#### 第 1 轮：让 AI 先"自陈理解"（不写代码）
```markdown
你正在协助我开发一个 Godot 4 的 2D 弹珠肉鸽项目。

▶ 启动协议
1. 先阅读 bible/_index.md
2. 根据本任务，只阅读相关的 Bible 文件
3. 先不要写代码。不要改文件。
4. 先告诉我：你认为本任务涉及哪些模块、会改哪些场景/脚本、
   有哪些规则还不明确。

▶ 任务
[详细描述 MVP 核心循环规则]

请先输出你的理解和问题，不要写代码。
```

**为什么第 1 轮不写代码**：
- AI 代码-writing 速度 > 你审代码的速度
- 让 AI 暴露它的理解和盲区
- 提前看到代码会落到哪几个文件（太多文件 = 任务不够小）

#### 第 2 轮：回答 AI 的疑问（不扩散新需求）
- 回答所有问题，并且**只回答这些**
- 不要"既然你提到了那要不要也做一下"——加新需求就开新会话

#### 第 3 轮：实现 + 测试

### 验证目标
> 验证"为什么好玩"——在有限球数下玩家兜兜转转；最后看自己能不能保住球数。游戏要给"轻微压力"和"还有机会翻盘"两个感觉。

## 第 12 课：上线前的性能与体验

### 定位
> ⚠️ 这不是必修课。在自己电脑上玩 → 可以跳过。
> 导出到 Steam Deck / 手机 / 微信小游戏 / 浏览器 → **必修**

### 性能预算（写入 bible/03_rules.md）
| 目标平台 | 帧率目标 | 不低于 |
|---------|---------|-------|
| PC（中端笔记本） | 60 帧 | 55 帧 |
| 手机 / Steam Deck | 30 帧 | 28 帧 |
| 微信小游戏 / 浏览器 | 30 帧 | 25 帧 |

其他预算：
- 命中粒子：每次最多 8 个，同屏总数不超过 60
- 弹珠：同屏不超过 20 条
- 帧率连续 1 秒低于"不低于线"后，自动降级（关粒子、降分辨率、合并 draw call）

### 四步循环
```
翻 Bible → 录性能报告 → AI 翻译瓶颈 → 一次只优化一个 → 重新录制对比
```

### 第 1 轮：录性能报告
```markdown
背景：我用 ____ 做了一款弹珠肉鸽，目标平台 ____，目标帧率 ____。

请帮我：
1. 这个引擎的性能录制工具叫什么？怎么打开？
2. 我应该录什么场景？录多长时间？
3. 录之前要不要做什么准备（关闭编辑器自身开销、用发布版不是开发版）？
4. 录完后看哪几个数字？发给你才能判断瓶颈在哪？
5. 我用我的电脑录的结果对低端机有参考价值吗？如何补录？
```

**新手最常踩坑**：
- ❌ 在编辑器里看帧率就开始改 → 编辑器本身就在吃性能
- ✅ 必须在**发布版 / 目标设备**录制
- 目标平台是手机 → 必须在手机上录

### 关键指标
| 字段 | 含义 | 关注点 |
|------|------|-------|
| performance/process_time | 脚本 _process 耗时 | > 8ms 太重 |
| performance/physics_time | 物理 _physics_process 耗时 | > 8ms 物理负载过高 |
| rendering/draw_calls | 绘制调用数 | > 500 有优化空间 |
| rendering/particles_drawn | 粒子数目 | 对比预算（≤60） |
| physics/collision_pairs | 碰撞对数 | 弹珠+钉子的物理量 |

### 第 2 轮：AI 翻译报告
```markdown
这是我测出来的性能报告（截图附后），场景：8 颗弹珠 + 150 颗钉子 + 粒子 + 屏幕震动。

请回答：
1. 大白话解释每栏含义
2. 画面/物理/脚本/内存，哪类是"真瓶颈"（砍掉一半能明显回帧）
3. 真瓶颈中最大的几个开销项
4. 按"性价比=收益÷工作量"排序优化建议
5. 哪些"看起来慢但便宜"的项不要碰？为什么？

不要写代码，只做诊断。
```

**关键洞察**：
- 看的是「**每帧花多少毫秒**」（60fps=16ms, 30fps=33ms）
- 不是「CPU 占用率」（80% 但只要帧率达标就没事）
- Physics 占比高 ≠ 代码有 bug，可能是 Geometry 配置不合理

### 第 3 轮：一次只动一个瓶颈
- 针对性改动，做完重新采报告
- **全面优化是反优化**——改 A 经常让 B 更慢

### 性能优化是横切关注点
- 变的是"实现方式"（对象池、信号解耦、合并 draw call）
- **不改变玩法**

## 第 13 课：从单干到组队开发

### 组队前三问（劝退段）
1. 有没有"想做的远超手能做"的具体清单？
2. 有没有愿意每周投入 ≥ 6 小时的互补人选？
3. 能不能接受"未来 2 周速度先慢后快"？

> 三答都"否" → 先别拉人

### 唯一必须先达成的共识
> **"X 模块意见不一致时，听谁的。"**

只解决**拍板权**，不解决"谁干活"——这是**唯一一个事后没法补救的东西**。

### 示例（4 人小队）
| 模块 | 拍板人 |
|------|--------|
| 玩法核心代码 / Bible | L |
| UI / HUD / 美术 | A |
| 数据与道具设计 | D |
| 工程与 CI | C |

### GitHub 三件套

#### 1. .gitignore
```
.godot/
.import/
*.import
*.translation
```
⚠️ `.godot/` 没忽略 = 把整个导入缓存推到云端，clone 一次 5 分钟。如果已经提交了：`git rm -r --cached .godot/`

#### 2. 分支：main + feature/*（两层就够了）
```
main        ← 永远可玩，clone 下来能直接跑
  ↑
feature/xxx ← 每个新功能一个分支，做完发 PR
```
❌ 不要一上来就 Gitflow（2010 年给桌面软件设计的，小团队没人遵守）

#### 3. PR 强制评审（唯一硬规则）
Settings → Branches → Add rule for main:
- ✅ Require a pull request before merging
- ✅ Require approvals: 1

### PR 30 秒检查清单
- ✅ clone 下来跑得起来吗？
- ✅ 改动是不是只改了 PR 标题说的那件事？
- ✅ **AI 有没有顺手"优化"了不相关的代码？**（最常见的 AI 副作用）
- ✅ 有没有把数据硬编码到代码而不是配置？

> 🔥 **为什么 AI 时代 PR 评审更重要？**
> AI 一次能写 200 行，但它也会自信地写错 200 行。
> Reviewer 的核心问题：「这次改动是不是只改了它该改的东西？」
> **90% 的 AI 问题都能被这个问题挡住。**

### AI 在协作中的角色
> **AI 不是团队成员，是每个人的私人工具。**
> - 不做群讨论，不给 AI 设角色 / 账号 / 平台
> - 每个人自己做卡片时，自己开 AI 会话，自己跑"翻 Bible → 自测 → 出代码"

### 团队规模
**2~4 人 + AI** 是最甜的小团队规模

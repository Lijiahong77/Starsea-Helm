4. 一次只优化一个，重新录制对比

## 提示词模板库

### A. Bible Context Prelude（每次对话固定前缀）
```
你正在协助开发一个 2D 弹珠机肉鸽游戏。
项目位于 docs/bible/。

开始任务时：
1. 先读 docs/bible/_index.md，提取本次涉及的文件路径清单
2. 根据任务只读最相关的文件
3. 复述你对当前任务的理解，先不要写代码
4. 命名和碰撞层请查阅 08_naming.md
5. 涉及新实体，查阅 02_entities.md
```

### B. 手感清单 Prompt
```
背景：这是我的弹珠肉鸽游戏。我录了一段 30 秒玩法流程（或口头描述）。

任务：从手感 / Juiciness 角度列出缺失或薄弱的反馈点。
约束：不要写代码、不要给具体参数数值。
按输入反馈 / 命中反馈 / 镜头反馈 / 音频反馈 / UI 反馈五类分别列。
每类说清"现在是什么、期望变成什么、为什么"。
优先排序：哪些是「不加就难受」，哪些是「锦上添花」。
列完后问"要不要先开始补？"
```

### C. 功能拆解 Prompt
```
请把"完整的弹珠肉鸽"拆解成功能清单，并按"是否唤起核心乐趣"排序。
核心循环：瞄准 → 蓄力 → 发射 → 看球弹 → 看球进不进袋洞 → 看球数有没有保住 → 想再发一发

输出表格：[功能名] | [P0/P1/P2/P3] | [一句话理由]
P0 = 不做就不是这个游戏
P1 = 做了核心乐趣才完整
P2 = 更好玩
P3 = 更高级，删了不影响核心

给出 MVP 范围声明（5 行以内），不要代码，只要范围划分。
```

### D. 性能报告翻译 Prompt
```
这是我测出来的性能报告（截图附后），场景：[弹珠数 + 钉子数 + 特效描述]

请回答：
1. 大白话解释每栏含义
2. 哪类是"真瓶颈"（砍掉一半能明显回帧）
3. 真瓶颈中最大的几个开销项
4. 按"性价比=收益÷工作量"排序
5. 哪些"看起来慢但便宜"的项不要碰？为什么？

不要写代码，只做诊断。
```

### E. 关卡设计 Prompt
```
为我的弹珠肉鸽设计 3 个关卡（热身 / 普通 / Boss），
难度曲线先慢后快。

每个关卡需指定：
- 图钉密度
- 袋洞位置和数量
- 时间限制
- 特殊机制（如有）

输出为可读的参数表，不要代码。
```

## 重要结论速览

### 选引擎（第 03 课）
- 2D 弹珠肉鸽 → **Godot 4**（100MB，启动 3 秒，GDScript，godot-mcp 成熟）
- 已有 Unity 经验 → Unity 也行
- UE → 不推荐（50GB，2D 物理拼凑，蓝图 AI 支持早期）

### 设计原则（第 01/05 课）
- 不要原创 → X-like + 一条微创新
- MVP 成功 = 朋友玩 3 分钟还想再玩
- 核心循环每个动词 = 必须做；没出现的 = 砍掉

### AI 协作铁律（贯穿全课程）
1. **先让 AI 说方案，再让它写代码**（第 02 课）
2. **一次只改一件事**（第 09 / 12 课）
3. **参数暴露到编辑器**，AI 给"旋钮"不给"数值"
4. **不要 hardcode** → JSON 配置文件
5. **不写 Bible 就用不了 AI**（第 02 课）
6. **PR 评审 = "这次改动是不是只改了它该改的东西？"**（第 13 课）

### 代码注释规范（铁律补充，2026-09-01 用户明确要求）
- **每个 .gd 文件顶部必须有文件头注释**：本文件职责、对应场景/数据结构位置、铁律提醒（零 hardcode、数值外置）。
- **每个函数 / 信号 / 常量组上方必须有注释**，说明「做什么、为什么」，不只写「是什么」。
- **非显而易见的写法必须写「为什么」**：Godot 4 坑、路径解析、坐标系约定、性能取舍、一次性诊断等，写清动机，方便人和 AI 复查对错。
- **复杂代码块逐段注释**（feed 管线、坐标系变换、JSON 读取、世界共享等），避免大段无说明代码。
- **注释用中文**，与开发对话语言一致。
- **禁止用注释掩盖 hardcode**：数值必须外置 `data/*.json`，注释只解释旋钮含义，不写死值。
- **验证先于声称**：改完必须 re-read 文件确认改动落地、再跑 MCP 抓输出（`errors` 为空 + 必要时采样像素）后才算修好，绝不凭"我以为改了"报成功。

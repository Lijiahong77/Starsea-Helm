> 第 01–05 课 | 课程目标：在 1 周内用 AI 把弹珠机肉鸽（Pinball Roguelike）的 MVP 做出来

## 第 01 课：找到你的第一个游戏灵感

### 三问法（唯一筛选标准）
1. **玩家在做什么？**（核心动词，不是主题）
2. **玩家感觉像谁？**（核心幻想 / 身份）
3. **2 周内能做完吗？**（MVP 时间盒）

### 关键心法
- **不要"原创"**，做「X-like + 一条微创新规则」
- 微创新 = 给原游戏的**爽点装放大器**
- 用 AI 评估方向，不要凭感觉选
- 让朋友玩 **3 分钟还想再玩第 2 局** → MVP 成立

### 游戏方向评估 Prompt
```markdown
# 角色设定
我是一个游戏开发新手，想做一个 2 周内能做完试玩的游戏。

# 任务
请帮我评估以下 3 个方向，从 5 个维度打分（1-5 分）：
1. 实现容易度
2. 体验清晰度
3. 美术类型匹配度
4. 传播潜力
5. 微创新潜力

# 方向候选
方向 A：【三问答案】
方向 B：【三问答案】
方向 C：【三问答案】
```

## 第 02 课：写出好用的 AI 提示词

### 核心理念：Bible（游戏圣经）
> **"对话会消失，文件才是 AI 团队的记忆。"**
> 这是"vibe coding"和"工程化用 AI"的**分水岭**。

### Bible ≠ GDD
| 文档 | 回答的问题 | 读者 | 形态 |
|------|-----------|------|------|
| GDD | 游戏整体怎么设计？ | 设计师 / 制作人 / 投资人 | 完整长文档 |
| **Game Bible** | 项目架构、世界规则、什么不准违反 | **程序 / 美术 / AI** | 碎片化、可索引的 wiki |
| Tech Doc | 架构设计、API | 程序员 | 技术文档 |

### Bible 三大属性
1. **可索引**：AI 不需要每次读全文，按需取一段
2. **声明式**：写"是什么"，不写"怎么实现"
   - ✅ `"球击中钉子，钉子消失，得 10 分"`
   - ❌ `"在 _on_body_entered 里调用 queue_free() 然后 score += 10"`（这是代码，不是 Bible）
3. **可追溯**：每条事实有出处（设计决策的日期 / 版本号）

### 判断标准
> 这条信息如果业务流程错了，它还成立吗？成立就写，否则就不写。

### 文件切分：按"耦合边界"
```
bible/
  index.md          ← 速查表（让 AI 学会按需读）
  01_core_loop.md
  02_entities.md
  03_rules.md
  04_physics.md
  05_ui_hud.md
  06_audio.md
  07_file_layout.md
  08_naming.md
  99_decisions.md
```

### 每个文件的骨架模板
```markdown
# 02. Entities (实体)
> 状态：WIP / 最后更新：YYYY-MM-DD / 关联决策：DEC-xxx

## 球 (Ball)
- 是什么：玩家发射的物理实体，受重力和碰撞影响。
- 数量上限：__ 颗（来自 03_rules.md#球数）
- 关键属性：质量、弹性、半径、初速度——具体数值在 03_rules.md
- 能做什么交互：钉子（消灭+得分），边板（反弹），地板（消失，不计分）
- 不能做什么：不能穿墙、不能与其他球碰撞（已在 DEC-003 记）
```

### 轻量备选架构：SPEC / MODULES / EXPERIENCE
适用于 Game Jam、原型 Demo、一周跑通玩法的小品项目：

| 文件 | 回答的问题 | 关键内容 |
|------|-----------|---------|
| SPEC.md | 这个游戏是什么、不是什么 | One-liner / 核心循环 / 关键数值边界 / Non-goals |
| MODULES.md | 项目里有哪些模块，各自负责什么 | 每个模块：职责 / 输入输出 / 依赖（不允许循环依赖）；mermaid 依赖图 |
| EXPERIENCE.md | 玩家应该感觉到什么 | 3–5 个体验关键词 / 关键时刻 / 反例（明确告诉 AI "不要做成 XX 那样"）/ 测试记录 |

### _index.md 是关键
```markdown
| 文件 | 负责 |
|------|------|
| [02_entities.md](/bible/02_entities.md) | 实体定义 |
| [03_rules.md](/bible/03_rules.md) | 数值规则 |
| ...
```

### 升级到模块化 Bible 的信号
- 模块超过 ~8 个
- MODULES.md 已经超过两屏
- AI 频繁忘记之前的决策
- 频繁需要文档来翻阅之前的上下文

### Context Prelude（每次对话固定前缀）
```markdown
你正在协助开发一个 2D 弹珠机肉鸽游戏。
项目位于 docs/bible/。

开始任务时：
1. 先读 docs/bible/_index.md，提取本次涉及的文件路径清单。
2. 根据任务只读最相关的文件，不要全文读取。
3. 复述你对当前任务的理解，先不要写代码。
4. 命名和碰撞层请查阅 08_naming.md。
5. 涉及新实体，查阅 02_entities.md。
```

### 最小工作流（5 步循环）
1. 立项 → SPEC.md 5 行内说清
2. 摸模块 → 每加一个模块，MODULES.md 补一段
3. 实测后 → 回填新决策、新边界到对应文档
4. 给 AI 下任务 → 按需挑选文档组合（调玩法 → SPEC+EXPERIENCE；写代码 → SPEC+MODULES；调优 → EXPERIENCE+测试记录）
5. 回填记录

## 第 03 课：搭建你的 AI 开发工具链

### 引擎选型（唯一决策依据）
> 这个引擎，能不能在 1 周内上手、后续完善游戏的时候方便改动？

只看两个维度：**AI 工具链成熟度** + **学习曲线**

| 维度 | Unity 2D | Godot 4 ⭐推荐 | UE 5 |
|------|---------|--------------|------|
| 弹珠物理 | ✅ | ✅ GodotPhysics2D 开箱即用 | ⚠️ Chaos 需自搭 |
| 体积/启动 | ~3GB 慢 | **~100MB 启动 3 秒** | ~50GB 启动 1 分钟+ |
| AI 工具链 (MCP) | unity-mcp 成熟 | **godot-mcp 节点级完整** | 早期 |
| 脚本语言 | C# | **GDScript（类 Python）** | C++/蓝图 |
| 学习曲线 | 中 | **低（只需学节点）** | 高 |
| 商店资产量 | 极多 | 中等 | 多但偏 3D |
| 收费 | 个人版免费 | **完全开源免费** | 个人免费+分成 |
| 推荐度 | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐ |

### 为什么 Godot 4 是首选
- GodotPhysics2D：RigidBody2D / StaticBody2D / PhysicsMaterial 开箱即用
- GDScript 对 AI 友好：Python-like，API 命名一致，tscn 格式类似 CSS，AI 容易编辑
- godot-mcp：AI 可以直接建节点、改属性、写脚本、跑场景
- 包小启动快：写完代码 F5 立刻跑

### 为什么 UE 不推荐做这个项目
- 安装 50GB，冷启动 1 分钟+
- 2D 物理需 Paper2D / Chaos 拼凑
- 蓝图 AI 工具链早期
- 精力花在"对抗引擎"而非"做游戏"

### Godot 安装步骤
1. godotengine.org 下载 Latest
2. 解压到**纯英文路径**（D:\Tools\Godot\），⚠️ 不要放桌面/我的文档
3. 双击运行 → 创建项目 `PinballRoguelike`，渲染器选 **Compatibility**
4. 切换到 2D 视图 → 打开输出面板（编辑器 → 编辑器面板 → 输出）
5. macOS：首次启动 Control+点击 → 打开

### MCP = 给 AI 装了一双"手"
- 接上 MCP 后，AI 能直接打开 Godot 工程、建节点、改属性、写脚本、跑场景
- 你只需要：决策 + 测试

### AI 客户端推荐
| 客户端 | 适合人群 | 备注 |
|--------|---------|------|
| **CodeBuddy（推荐）** | 完全新手 | 内置 MCP 管理，中文界面，零配置 |

### 关键速记
- 引擎：**Godot 4.x（4.3+）**
- 语言：**GDScript**
- AI 客户端：**CodeBuddy**
- 协议：**MCP（godot-mcp）**
- 项目名：`PinballRoguelike`
- 路径：**全英文、无空格、无中文**

## 第 04 课：用 AI 跑出第一个可玩版本

### 开工前体检
1. 场景树：`Main → Floor → Ball` 结构正常
2. 能跑：F5 后球能掉下来、撞地板弹一下
3. MCP 接通：工程路径指向 project.godot 所在目录

### 完整 Prompt 模板（可直接复用）

```markdown
我现在用 Godot 4 做一个弹珠机肉鸽游戏（柏青哥风格）。
当前场景 Main.tscn 里已有：Floor (StaticBody2D) + BallTemplate (RigidBody2D, Visible 关闭, Freeze 开启)
视口：1920×1080（项目设置已固定）

任务：
# 一、创建白盒物理边界（墙体）
LeftWall: x=0, w=20, h=1080
RightWall: x=1900, w=20, h=1080
Ceiling: y=0, w=1920, h=20
都是 StaticBody2D + RectangleShape2D

# 二、创建图钉阵（Pegs）
- 父节点 PegBoard (Node2D)
- y=300 到 y=700 之间，6 行，每行 10~12 个，行列间距 128px
- 每个图钉 Area2D + CollisionShape2D (圆形, 半径 12) + Sprite2D (白色小圆点)
- 不需要脚本

# 三、创建发射器（Launcher）
- 位置 (1600, 900)
- 左键按住连续发射，松开停止
- 关键参数用 @export 暴露：
    fire_interval: float = 0.15
    launch_impulse: float = 800.0
    launch_angle_jitter_deg: float = 15.0
- 新球从发射器位置创建，apply_central_impulse 施加冲量
- 方向向上 + 左右随机偏移 jitter 度
- 球飞出屏幕底部 (y > 1100) 自动清理
- 不要改变 Floor 和 BallTemplate

所有新节点挂在 Main 下。开始吧。
```

### 为什么需求要这么细
- AI 代码质量 ≈ 需求的清晰度
- 关键数字（视口、行列数、间距）必须写死在需求里
- "帮我做个弹珠机" → AI 只会给你一个写实弹珠台贴图

### 工作流
```
AI 复述方案 → "方案 OK，请直接动手" → 看 AI 干活 → 扫代码 → F5 试 → 出问题精准描述给 AI
```

### 关键代码点
| 代码 | 作用 |
|------|------|
| `@export var fire_interval = 0.15` | 暴露到 Inspector，拖滑块改数值 |
| `template.duplicate()` | 复制模板球，继承所有物理参数 |
| `apply_central_impulse(...)` | 给球瞬间冲量，物理引擎接管 |
| 随机角度偏移 | 扇形散开，不是一条直线 |

### 调试心法
- 不要"不工作"，要描述**看到了什么**
- 报错直接贴报错文本
- 表象 → 原因 精准描述

## 第 05 课：用 AI 拆解功能与规划开发

### 三个里程碑（顺序不能反）
| 术语 | 回答的问题 | 长什么样 | 验收标准 |
|------|-----------|---------|---------|
| **Prototype** | 技术上做得出来吗？ | 美术全色块，可能没有完整循环 | 跑得通、卡顿可接受 |
| **MVP** | 核心循环好玩吗？ | 白盒/占位图，完整 开始→玩→结算 闭环 | 玩家能感受到核心乐趣 |
| **Vertical Slice** | 玩家会买账吗？ | 某一段用最终品质，5–15 分钟可玩 | 可拿去给发行商看 |

> MVP 是一个**商业可行性假设**，原型不是。先 rapid prototyping，再 polish。

### 弹珠肉鸽核心循环
```
瞄准 → 蓄力 → 发射 → 看球弹 → 看球进不进袋洞 → 看球数有没有保住 → 想再发一发
```
**每一个动词都是 MVP 必须做的**；没有出现的全部砍掉（成就、存档、社交……）

### AI 功能拆解 Prompt
```markdown
# 背景
我正在做一个 2D 弹珠肉鸽游戏，目前已完成：
- 发射器（按住左键连续射球）
- 白盒图钉阵 + 边框
- 所有关键参数暴露在 Inspector

# 任务
请把"完整的弹珠肉鸽"拆解成功能清单，并按"是否唤起核心乐趣"做优先级排序。
核心循环：瞄准 → 蓄力 → 发射 → 看球弹 → 看球进不进袋洞 → 看球有没有保住 → 想再发一发

# 约束
1. 输出表格 3 列：[功能名] | [优先级 P0/P1/P2/P3] | [一句话理由]
2. P0 = 不做就不是这个游戏；P1 = 做了核心乐趣才完整
   P2 = 更好玩；P3 = 更高级，删了不影响核心
3. 给出 MVP 范围声明（5 行以内说清做什么 / 不做什么）
4. 不要给我代码、不要实现细节，只要范围划分
```

### 产出物
```
docs/
  ├── MVP_Scope.md       # 范围声明
  ├── Core_Loop.md       # 核心循环定义
  └── Priority_Backlog.md # 功能优先级清单
```

### AI 输出的参考 P0/P1 分级
| 功能 | 优先级 | 理由 |
|------|--------|------|
| 钉子击中检测与消除 | P0 | 撞钉不消失=没有反馈 |
| 分数系统 | P0 | 消除必须兑成可见分数 |
| 袋洞系统 | P0 | 核心循环"看球进不进袋洞" |
| 弹珠数量管理 | P0 | 核心循环"球数有没有保住" |
| 橙色钉子 + 分数倍率 | P1 | Peggle 灵魂，Fever 来源 |
| Fever 狂热模式 | P1 | 清完橙色钉的奖励兑现 |
| 额外弹球奖励 | P1 | 主动把球数补回来 |
| 结算动画 | P1 | "想再来一发"的诱因 |

### 关键判断
- 朋友**只玩 3 分钟还想再玩** → MVP 成立
- MVP 开发周期通常 **≤ 2 周**
- AI 帮你排优先级，但**拍板在人类**

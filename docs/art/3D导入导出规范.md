# 3D 资产导入 / 导出规范（Origin · Forward · Scale）

> 最后更新：2026-09-14
> 用途：**每一个要进游戏的 3D 模型**（飞船/炮塔/敌人/舱室）在 Blender/建模软件里导出前，按本文对齐「原点、朝向、单位、命名」。
> 为什么单独成文：这些约束**不是审美问题，是坐标问题** —— 引擎里所有摆位都由代码按 `data/*.json` 的数值算，模型原点一歪，代码算得再对也会表现为「炮塔陷进船体」「敌人鼻子朝后」。错了不会报错，只会静默错位。
> 与 `ASSET_WISHLIST.md` 的分工：清单管「要哪些素材」；本文管「拿到素材后怎么摆才对」。

---

## 零、一句话结论（先看这个）

| 模型 | 原点（Cursor）放哪 | 朝向约定 | 单位/尺度 |
|------|-------------------|---------|-----------|
| **飞船本体** | 舰体几何中心（船中） | **船头 = +Z** | 1 单位 = 1 米，长 64 / 宽 22 / 高 16 |
| **主炮** | **旋转轴在炮座底部**，不居中 | 炮口 = +Z | 最长边 6–8 m |
| **副炮 / 各种副炮型号** | **旋转轴（底座圆心）在炮座底面中心** | 炮口 = +Z | flak ~3 / gatling ~2.1 / lance ~4.3 m |
| **敌人** | 几何中心 | 机头 = +Z | 6 / 14 / 20 m |
| **舱室（内壁）** | 房间中心（地面中点） | — | 净空 6.0(深)×5.0(宽)×3.0(高) m |

> ⚠ 上面「炮口/机头 = +Z」是**全项目统一约定**，来源是 `Sectors.AXES`：`fore = +Z`（艏部舷窗在 z=+1.8，实测自 `bridge_whitebox.tscn`，不是猜的）。

## 一、总原则：原点 = 代码将要旋转它的那个点

模型原点（Blender 里的 Object Origin / cursor）在引擎里就是**节点的 `position`**。项目里所有摆位都是代码按 JSON 数值算的：

- 炮塔：`Turret.snap_to()` 执行 `global_position = muzzle_pos`，`muzzle_pos` 来自 `turrets.json` 的 `mount`（副炮由 `axis × hull_radius` 推导）。
- 敌人：`Enemy.setup()` 执行 `global_position = spawn_pos`。
- 舱室：`.tscn` 里每个 MeshInstance 有自己的 `transform`。

**所以原点必须放在「逻辑上代表这个物体的那个点」**。放错的表现（都不报错，只是看起来不对）：

| 原点放错 | 表现 |
|---------|------|
| 炮塔原点放几何中心（而不是底座） | 炮塔**一半陷进船体** —— 因为代码认为"原点贴船面" |
| 炮塔原点放炮口尖端 | 炮塔整个**飘在船外** |
| 敌人原点放机头 | 敌人在绕飞时**以机头为圆心画圈**，看起来像甩尾 |
| 舱室原点放房间角落 | 房间与舷窗/控制台**整体错位** |

**判据**：问自己「代码是要把这个点钉在某个位置，还是要绕这个点旋转？」
- 钉位置（敌人、飞船）→ 放**几何中心**（或约定基准点）。
- 绕点旋转（炮塔）→ 放**旋转轴**（炮座的旋转中心，通常在底座中央）。

## 二、飞船本体（Ship）

**现阶段状态**：`scenes/bridge/bridge_whitebox.tscn` 里船体是**白盒**（6 面 Wall + 舷窗框 + 控制台），不是一整块模型。真船体模型属 `ASSET_WISHLIST §①` 舱室套件。

**尺度（权威源 `presentation.json › ship`）**：
```
length = 64 m   width = 22 m   height = 16 m
```
副炮挂载点由 `turrets.json › sub_gun_instances` 的 `hull_radius` 推导：
`mount = axis × hull_radius`，其中 `11.5 = width/2 + 0.5 = 11 + 0.5`。

**原点要求**：**舰体几何中心**（船中，约在长度 32 m 处、宽高各自的几何中心）。

**朝向要求**：**船头朝 +Z**。这条不能改，理由：
- `Sectors.AXES[fore] = (0,0,1)`，舷窗在 z=+1.8、尾墙在 z=-4.4。
- 4 路 feed 相机、4 个舷外标记、敌人进场方向全部基于该约定。
- 改朝向 = 全项目坐标系重算，代价极高。**顺着它以 +Z 为船头就好。**

**为什么原点在中心而不是船头**：船默认静止（bible「飞船全局唯一，静止」），原点在中心让 `axis × hull_radius` 这类对称推导（左舷 -X、右舷 +X、上 +Y、下 -Y）自然成立。若原点放船头，所有 `hull_radius` 公式都要加偏移，得不偿失。

## 三、炮塔（Turret）· 原点 = 底座旋转中心 ★最容易错

**这是本规范最关键的一节。** 炮塔和敌人不一样：敌人整体位移，**炮塔要绕轴转**（可转塔的副炮要瞄准、要扫射）。

**原点要求**：**炮塔底座（旋转中心）在该几何的旋转轴线上**，且 **Y 方向贴齐安装面（底座底面 y = 0）**。
- 水平旋转轴 = 过原点的 **Y 轴**。
- 原点**不要**放几何中心。否则炮塔装上去会一半陷进舰体（见 §一 表）。

**朝向要求**：**炮口朝 +Z**。
- 主炮固定朝 `fore`（+Z），直接对齐即可。
- 副炮装到四向扇区时，引擎会把模型绕 Y 转 90°/180°/270° 指向各扇区外法线（`Sectors.AXES`）。所以**建模时只需做「朝 +Z」这一个方向**，四个方向由引擎旋转复用 —— 这是「做一套、转向复用」的关键，别在 Blender 里做四份。

**尺度**（白盒 `visual_size` 是相对值，真实米数按敌人 6–20 m 自洽推断，详见 `炮塔提示词.md`）：

| 型号 | 建议最长边 | 关联数据 |
|------|-----------|---------|
| 主炮 | 6–8 m | `main_gun`（hp 200，固定） |
| flak 标准点防炮 | ~3 m | hp 80 / 单发 24 / 3.0 s |
| gatling 速射近防炮 | ~2.1 m | hp 60 / 单发 12 / 1.5 s |
| lance 重型穿甲炮 | ~4.3 m | hp 110 / 单发 54 / 4.5 s |

> **Y 贴齐安装面的实现**：在建模软件里把"炮塔装在船面上的那个底面"对齐到世界 y=0，然后整体 Apply Transform（应用变换，让原点与几何关系固化）。导入 Godot 后**不要再**在视觉子节点上手动调 y 偏移 —— 代码只认 `muzzle_pos`。

**三向复用的验证**（DEC-052 起底部无炮）：导入后把炮塔分别摆到 port/starboard/dorsal 三个 mount 上，确认炮口都朝各扇区外。若某个方向炮口朝里，是引擎旋转逻辑问题，不要去改模型。

## 四、敌人（Enemy）

**原点要求**：**几何中心**（`Enemy` 在 `setup()` 里 `global_position = spawn_pos`，movement 直接改 `global_position`）。
- 敌人是**整体位移 + 绕飞**，绕飞的圆心是 `_center`（船心），**不是敌人自身原点**。所以敌人原点居中即可，不影响绕飞轨迹。
- 若原点放机头，`Enemy` 的 `global_position` 就会落在机头上，视觉上表现为"绕飞时甩尾、进场时鼻子伸太远"。

**朝向要求**：**机头朝 +Z**（与 `炮塔提示词.md` / `敌人飞船提示词.md` 一致）。

**尺度（权威源 `enemies.json` 的 `size`）**：小型 6 m / 中型 14 m / 重甲 20 m。

> 注：敌人的**碰撞不走模型网格**（用 `CollisionShape3D` 球/盒近似），所以即使模型非水密、原点略偏也不致命 —— 但仍建议按规范做，避免视觉与碰撞体错位。

## 五、舱室（Bridge Interior）· 两个额外坑

`ASSET_WISHLIST §①` 的舱室套件，除了原点，还有两个**只有内壁模型才有的坑**：

1. **法线朝内**：舱壁/地板/天花板是**内壁**。外部模型法线通常朝外，从房间里看会**整面透明**。解法二选一：
   - 建模时翻转法线朝内；
   - 或材质开 `cull_mode = disabled`（双面渲染）。
2. **舷窗不能做成整圈玻璃**：`DEC-026` 的微创新 = **只有艏部一面舷窗**。做模型时手滑做成环形玻璃 = 直接毁掉「信息不对称由物理保证」这条承重墙。

**原点要求**：**房间中心**（地面中点，x=0, z=0, y=底面）。白盒参照（实测自 `bridge_whitebox.tscn`）：
- 房间净空 `6.0(进深, z) × 5.0(宽, x) × 3.0(高, y)`；
- 艏墙（舷窗那面）在 z=+1.8，尾墙 z=-4.4；
- 舷窗开口 **4.4 宽 × 1.3 高**，窗台高 **0.95 m**；
- 玩家眼高 **1.60 m**，即 `Camera3D` 在 Player 局部 y=+1.6。

> 导入后**先按最长边锚定米数，再摆位**（清单工程通则第 2 条）。别让模型"看着差不多"。

## 六、通用导出设置（Blender → .glb）

| 设置项 | 应为 | 理由 |
|--------|------|------|
| 格式 | **`.glb`**（单文件） | Godot 4 原生导入，Git 友好（`ASSET_WISHLIST` 工程通则第 1 条） |
| 单位 | **米（Meter, Scale=1.0）** | 与 `ship.length=64` 等数值同一量纲；导出时勾「+Y Up」（glTF 默认），Godot 会自动转成 Y-Up |
| 变换 | **导出前 Apply Transform（Ctrl+A）** —— 详见下方 §六之二 | 把旋转/缩放固化进网格，防止引擎里出现非单位 scale 导致的光照/物理异常 |
| 朝向 | **场景里先摆成 +Z 朝前再导出** | 见 §三；注意 Godot 默认前向是 -Z，本项目反用 +Z，必须显式处理（见 §六之一） |
| 命名 | 有意义、无空格（如 `turret_lance`） | 进 Godot 后节点名即资源名；空格与中文易在脚本路径里翻车 |
| 材质 | 简单 PBR 即可（albedo + emission） | 白盒阶段代码用 `material_override` 接管；真材质后续替换 |

## 六之一、⚠ 朝向：Godot 默认 -Z，本项目反用 +Z

**Godot 引擎的通用前向约定是 `-Z`**（相机、`look_at`、`Vector3.FORWARD` 都是 -Z）。但**本项目把船头/炮口/机头定成了 +Z**（因为 `Sectors.AXES[fore] = (0,0,1)`，是既成事实，全项目所有摆位公式都依赖它）。

这两件事**冲突**，必须显式处理，不能靠默认值。三种做法，选一：

| 做法 | 操作 | 评价 |
|------|------|------|
| **A. 建模时朝 +Z（推荐）** | 在 Blender 里让炮口/机头指向 **+Z**，导出后在 Godot 里**不要**旋转根节点 | 最直接；模型与项目坐标一致，"所见即所得" |
| B. 按 Godot 默认真 -Z 建 | 导出后在 Godot 里把根节点绕 Y 转 180° | 多一步手工操作、易忘；不适合本项目 |
| C. Blender 导出器换轴 | Blender glTF 导出器有 `+Y Up` / 轴转换选项，可把 Blender 的 -Y 前向映射成 +Z | 可行但要在**每个导出**都记得勾对；一旦漏勾就静默反了 |

> **推荐 A**。理由：本项目已经整体 +Z，模型顺着它走，就不存在"引擎默认"与"项目约定"打架的问题。**关键判据**：导入 Godot 后**不要**为了让模型"看起来朝前"而手工旋转根节点 —— 旋转根节点会连原点一起转，把 §三 好不容易对齐的旋转轴又转歪。

**Blender 里的具体摆法（做法 A）**：建完模型后，把炮口朝向世界 **+Z**（Blender 的 Z 轴向上，此处指**导出后**对应 Godot 的 +Z，即 Blender glTF 导出器换算后的前向）。最稳的验证：导出 `.glb` → 拖进 Godot → 看 `Sectors.AXES[fore]`(+Z) 方向是否就是炮口方向。

## 六之二、变换（位置/旋转/缩放）要清除吗？—— 要，但分清"清在哪一层"

**结论：在建模软件里 Apply Transform（把变换烘焙进网格），让导出的物体**变换=单位矩阵**。但"清除"的语义分两层，别搞混。**

### 层次一：建模软件里的 Object Transform → **必须 Apply**

Blender 里每个物体的 `Location / Rotation / Scale` 是**存在节点上的**。导出 `.glb` 时这些值会被写进文件，Godot 导入后会**原样出现在节点 Transform 上**。后果：

- **未 Apply 的 Scale**：缩放被留在节点上而不是网格里。Godot 里若再调这个节点（比如代码里 `t.scale = ...`，`swap_turret` 换装特效就干这个），会**累积缩放**，结果不可预测。
- **非均匀缩放（non-uniform scale，如 (1, 2, 1)）**：与旋转组合会产生**切变/倾斜（shear）**，渲染变形；更糟的是 `CollisionShape3D` 会算错。**任何非 1:1:1 的缩放都必须 Apply。**
- **未 Apply 的 Rotation**：Godot 里表现为节点带着一个初始旋转，你再定位时会觉得"怎么歪的"。

**操作**：Blender 里选中物体 → `Ctrl+A` → **All Transforms**（或分别 Apply Location / Rotation / Scale）。之后物体的 Transform 归零，几何本身"长"在正确的世界位置上。

> ⚠ **但"Apply Location"要慎用，看模型类型**：
> - 炮塔/敌人这类**原点有明确语义**的（旋转轴 / 几何中心）：**先摆好原点位置，再 Apply All** —— Apply Location 会把原点锁在世界原点，所以**要在 Apply 之前就把 pivot 放到正确位置**（用 `Origin to ...` 或手动设 origin）。
> - 否则会出现"Apply 完原点跑到世界原点，炮塔又陷进船体"。

### 层次二：Godot 导入时的根包装节点 → **不要动它**

Godot 4 导入 `.glb` 会**自动创建一个根节点**（默认是个 `Node3D`，包住整个模型层级）。这是 Godot 的固定行为，不是错误。

- **不要**为了让模型显示正确，去旋转/缩放这个根节点 —— 那会连原点一起改。
- 正确的原点/朝向由**建模阶段**（层次一）保证，导入后根节点应当是**单位变换**。
- 若导入面板里 `Root Scale` 不是 1.0 或根节点带了旋转：说明建模阶段的变换没清干净，**回建模软件重做层次一**，不要在 Godot 里"就地修"。

### 一句话记忆

> **建模软件里 Apply（把变换烘进网格），Godot 里不碰根节点。**
> "清除变换"清的是**建模软件的 Object Transform**，不是对着 Godot 的导入根节点做手术。

---

**导入后的 4 步（复述 `ASSET_WISHLIST` 工程通则，勿跳）**：
1. 调 scale 使最长边 = 规范里的米数（若建模时已按米建好，这步应已是 1:1，只需确认）；
2. 确认原点与朝向（本文各节）—— 根节点应为单位变换；
3. 接入 spawn 逻辑（炮塔→`TurretSystem`，敌人→`EnemySystem`）替换占位 Mesh；
4. 跑一次对应测试套（headless）确认没把坐标搞崩。

## 六之三、导出前的标准作业顺序

模型从"建模完成"到"进游戏"，按这个顺序做（每步都独立可验证）：

1. **合并重合顶点** —— 重复导入常留下"位置重合但拓扑分开"的虚焊点，会让法线分裂/体积膨胀。用 `docs/tools/` 里的 Blender 合并工具（`README_重合顶点合并.md`）。**先做这步**，否则后面的 Apply/导出都建立在脏拓扑上。
2. **Apply Transform**（Ctrl+A → All Transforms）—— 见 §六之二。**注意 Apply Location 前先把 pivot 放对**。
3. **摆朝向**（+Z 朝前）—— 见 §六之一。
4. **导出 `.glb`**（米、+Y Up、命名无空格）。
5. **导入 Godot** → 确认根节点是单位变换 → 接 spawn → 跑测试。

> 1 和 2 是两件不同的事：**合并顶点**清的是"拓扑重复"，**Apply Transform** 清的是"节点变换"。都要做，且顺序不能反。

## 六之四、模型到手，先跑一次探针（30 秒，省一天）

`.glb` 是二进制，拖进引擎前**看不出两件要命的事**。用 `docs/tools/_probe_glb.py` 直接读它的元数据，不启动 Godot / Blender：

```bash
python docs/tools/_probe_glb.py assets/models/你的模型.glb
```

给出：**① 世界包围盒（真实米数）② 材质 doubleSided ③ 面数 / 贴图数 / 节点树**。

**为什么必要 —— 两条最容易翻车的：**

1. **材质 `doubleSided`**（决定"从内部看是什么"）：

   | 字段 | Godot `cull_mode` | 从模型内部看 | 谁要这个 |
   |---|---|---|---|
   | `false` 单面 | 背面剔除 | **透明**（看得见外面） | **船壳 / 外壳** |
   | `true` 双面 | 关闭 | **实心壁**（挡住视线） | **舱室内壁** |

   ⚠ **这条不能假设**。同一个导出器，材质里勾没勾 Backface Culling，会产出**完全相反**的结果。
   （2026-09-16 实录：我以为"glb 默认就是单面、船壳天然从内部透明"，探针一跑发现是
   `doubleSided: True` —— 船壳从内部是实心壁，判断当场翻车。）
   改法：Blender 里勾 Backface Culling 重导，或 Godot「Advanced Import Settings」里改该材质的 Cull Mode。

2. **尺度**：建模软件里的 `1.118` 可能是 1.1 m，也可能是 1.1 km。**包围盒最长边就是答案**，
   别在引擎里靠"看着差不多"调 scale（§七 第 3 句说的就是这个）。
   目标尺度见本文各节表（飞船 64 / 炮塔 3–4.3 / 敌人 6–20 m）——差多少倍，缩放因子就是多少。

> 附带体检：面数（性能预算）、贴图张数与体积（仓库体积 / 是否该上 LFS）、节点树（能不能分件）。

## 七、速查：一个模型进游戏前问自己 6 句

1. **原点**放对了吗？（炮塔=底座旋转轴 / 敌人=中心 / 飞船=船中 / 舱室=房间中心）
2. **朝向**是 +Z 吗？（炮口 / 机头 / 船头 —— 注意 Godot 默认是 -Z，本项目反用 +Z，见 §六之一）
3. **变换** Apply 了吗？（Ctrl+A → All Transforms；特别是缩放必须 1:1:1，非均匀缩放会切变+碰撞错）
4. **Godot 里的根节点**是单位变换吗？（导入自动加的包装根节点不要手工旋转/缩放，要改就回建模软件）

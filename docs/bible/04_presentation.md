## 零、一句话立场

> **战场是 3D 的，界面是 2D 的。**

| 是 3D | 是 2D（Overlay UI） |
|-------|-------------------|
| 舰桥舱室、舷窗、控制台 | 装配界面、HUD、战损报告 |
| 六扇区空间、敌人来袭轨迹 | 接管时的准星 / 伤害数字 |
| 炮塔模型、主炮弹道、爆炸 | 可选 2D 雷达总览（Overlay） |
| **控制台上的副炮实时画面（Viewport 贴图）** | |

这条边界不划清，会掉进「把所有东西都做成 3D」的坑（DEC-010 已砍掉 3D UI）。

## 一、渲染器与技术底座

**渲染器 = Forward+**（用户 2026-08-30 拍板）

| 项 | 选择 | 理由 |
|----|------|------|
| 渲染器 | **Forward+** | 舱室有大量自发光表面（监控屏）+ 需要辉光 + 少量点光，是 Forward+ 的强项 |
| 抗锯齿 | **MSAA 2x–4x**，**不用 TAA** | ⭐ **监控屏上的文字 / 角标 / feed 画面必须清晰可读**（信息主通道）。TAA 会让 UI 纹理与 Viewport 贴图发糊 |
| 色调映射 | **Filmic** 起步；过曝严重改 **AgX** | 绝对不要 Linear |
| 辉光 | 阈值 0.8–1.0，强度 0.4–0.8 | 屏幕自发光的氛围来源 |
| 主光 | DirectionalLight ×1（冷白偏蓝，模拟远处恒星） | 不投影，或只对舰体投影 |
| 补光 | OmniLight **只给 2–3 块主屏** | 光源数量是 Forward+ 主要开销 |
| 屏幕发光 | **Emission 材质 + Glow，不配真光源** | 每块屏各配一盏灯 = 光源爆炸 |
| SDFGI | **Prototype 阶段关闭** | 占位阶段不需要间接光，VS 再试 |
| ReflectionProbe | ×1，舱内 | 屏幕反光打在金属舱壁，氛围收益极高 |
| 星空背景 | **ShaderMaterial 程序生成**，不用 HDRI | 比全景 HDRI 轻得多，无需外部资源 |
| near / far | 0.1 / 1500 | 深度精度与远景平衡 |

## 二、单位尺度：1 unit = 1 米

采用 Godot 默认（1 单位 = 1 米），与物理默认值自洽。

### 三个约束反推出全部尺度

**约束 ①｜人的尺度必须真实**
玩家肉身在舰桥里，第一人称沉浸感全靠尺寸对。天花板 3 m、门 2.1 m、控制台 0.95 m 高 —— 不对就秒出戏。

**约束 ②｜舷窗视野角是几何算出来的，不是拍脑袋定的**
DEC-026 说「舷窗只朝前、约 100–120°」。这个角度是**算出来的**：

```
视野全角 = 2 · atan( 舷窗宽度 / 2 / 玩家到玻璃的距离 )
```

| 舷窗宽 | 站位距离 | 视野全角 | 效果 |
|--------|---------|---------|------|
| 3.6 m | 2.2 m | **79°** | 窄 —— 监控更刚需 |
| 4.4 m | 1.7 m | **105°** | ⭐ 默认（落在区间内） |
| 5.0 m | 1.4 m | **122°** | 宽 —— 上限，监控易被忽略 |

⭐ **推论**：想调「监控有多必要」，调 `bridge.viewport_width` 和 `bridge.console_distance` 这两个几何量，**不要去调「视野角度」参数**。角度是结果不是原因。

**约束 ③｜威胁窗口 ≥ 8 秒（玩家反应时间）**
主炮**不再机动**（DEC-030），所以这里不是「转向延迟」，而是**玩家从发现到接管的总反应链**：

```
余光扫到某路 feed 有压力 → 判断（~2 s）→ 接管（点该路 feed 或按 1–5，切换本身 < 0.5 s）→ 手动提速清场
```

留 2.5 s 余量 → **敌人从进场到接触，必须 ≥ 8 秒**，否则「提前预判并接管」相对于「事后补救」没有优势，DEC-021 的决策就失去意义。

```
行程 = 进场半径 − 攻击距离 = 190 − 50 = 140 m
```

| 敌人 | 速度 | 行程时间 | 判定 |
|------|------|---------|------|
| 小型战机 | 14–20 m/s（取 17） | **8.2 s** | ✓ 刚好达标（最脆，窗口短一点合理） |
| 中型轰炸机 | 9–13 m/s（取 11） | **12.7 s** | ✓ |
| 重甲单位 | 6–10 m/s（取 8） | **17.5 s** | ✓ 慢是特性 |

**敌人速度偏慢是刻意的** —— 本作低 APM，玩家必须有读屏时间。不要为了「打击感」把速度调快。

**约束 ④｜进场时要在屏幕上看得见（1080p 默认）**
1080p（垂直 1080px）、垂直 FOV 70° → 0.0648°/px。进场半径 190 m 处：

| 敌人 | 尺寸 | 角直径 | 屏幕高度（1080p） |
|------|------|--------|-----------------|
| 小型战机 | 6 m | 1.81° | **27.9 px** ✓ |
| 中型轰炸机 | 14 m | 4.22° | **65 px** ✓ |
| 重甲单位 | 20 m | 6.02° | **93 px** ✓ |

> 1080p 下小型战机进场 27.9 px，比 720p 的 18.6 px 宽裕。**Q10（是否提到 1600×900）现在不急**，1080p 已达标。若实测看不清，先调敌人尺寸，不要先调进场半径（会破坏约束 ③）。

### 尺度总表

| 对象 | 尺寸 | 备注 |
|------|------|------|
| **舰桥净空** | 6.0（进深） × 5.0（宽） × 3.0（高）m | 玩家背后 4.0 m 到后墙，身前 1.7 m 到玻璃 |
| 玩家眼高 | 1.60 m | 站在主控制台后（不走动） |
| 舷窗 | 宽 4.4 × 高 1.30 m，窗台高 0.95 m | 窗上沿 2.25 m，眼高 1.60 居中偏下 ✓ |
| **飞船本体** | 长 64 × 宽 22 × 高 16 m | 轻型护卫舰；舰桥在艏部上层，舷窗朝前 |
| 主炮 | **固定艏部正面**（不转塔、只打前） | 可多门叠加，有可见弹丸 |
| 副炮间距 | 相邻 18–26 m | 决定「打的是哪个扇区」在视觉上可分辨 |
| 炮塔射程 | 100 – 140 m | 交火区 = 射程 → 攻击距离 ≈ 45–60 m |
| 主炮弹丸速度 | 150 – 250 m/s | 飞行 0.2–1.3 s，**肉眼可见弹道** |
| 副炮弹丸速度 | 200 – 400 m/s | 飞行更短、弹道同样可见（DEC-034 9/1 修订） |

> ⚠️ **必做项（DEC-034 · 9/1 修订）**：**主炮与副炮都发射离散弹丸**（一发发打，非持续光束 / 非瞬时扣血）。
> 差别**只在「谁算提前量」**：
> - **主炮**：弹丸慢（150–250 m/s），玩家手动接管时**由玩家自己瞄、自己算提前量** → 需 `LeadPrediction` 给出预测标记辅助瞄准。
> - **副炮**：自动锁敌，**系统自动计算提前量**后发射；玩家不手动瞄，故玩家层面不需要做提前量。

### 校验：尺度下玩法成立吗？

```
敌人从 140 m 外射程进入 → 交火区 45–60 m
小型战机 17 m/s → 交火时间约 5–9 s
副炮单门自动 DPS 5–12，杀一个小型（HP 15–25）需 2–4 s
每面同波 2–4 个敌人 → 单门自动清不完
→ 敌人抵达攻击距离 → 打炮塔耐久 → 该面失守风险上升
```

✅ **逻辑自洽**：交火时间不足以自动全歼 → 炮塔必然掉耐久 → 失守链成立（DEC-031）。
**若实测敌人根本摸不到炮塔，说明射程或 DPS 调过头了，失守链会失效。**

## 三、相机参数

| 字段 | 值 / 区间 | 理由 |
|------|----------|------|
| `camera.fov` | **65 – 72**（起步 70，垂直） | 低于 60 舱内压迫；高于 80 边缘畸变让屏幕文字糊。70 是空间感与可读性平衡 |
| `camera.near` | 0.08 – 0.12 | 太近会穿模看到舱体外壳内侧 |
| `camera.far` | 1200 – 2000 | 够放星空与远景 |
| `camera.pitch_limit` | ±75 – 85° | 不要 ±90，万向锁附近会抖 |
| **yaw** | **360° 自由** | ⚠️ 见下方说明 |
| `input.mouse_sensitivity` | 倍率 0.5 – 3.0，基准 0.0022 rad/px | 必须可调，手感第一关 |
| `camera.idle_sway_amp` | 0 – 0.006 m | 极轻微呼吸感。**不做 head bob**（玩家不走动） |
| `camera.idle_sway_period` | 4 – 6 s | |
| `feel.shake_max_offset` | 0.01 – 0.05 m | Game Feel ③。**三轴正弦叠加要按模长夹到上限**，否则旋钮值是谎言。Overlay UI 天然免疫抖动，白拿的好处 |
| `feel.zoom_in_time` / `zoom_out_time` | 0.03 – 0.08 / 0.12 – 0.25 s | Game Feel ④。进干脆、出柔和；视场角收窄量按事件给（见 `feel.events`），单次 ≤ 4°，超过会晕 |

### ⚠️ 重要：yaw 自由 360°，但舰桥只有艏部一面舷窗

玩家能自由转身，但**转身后看到的是舱壁**（监控屏在控制台，不是外景）。

这一条是 **DEC-026（信息不对称）的物理保证**。若四面玻璃，玩家转头直接看后面 → 监控失去意义 → 微创新崩塌。

> 🚧 **建白盒时的硬要求**：只有 +Z（艏部）那一面开窗，其余五面实心舱壁。第一天就要做对。

**REFIT 阶段**：相机固定在控制台前不动，装配界面是 2D UI 全屏覆盖。

## 四、舰桥布局：监控屏放在哪

> 原则：**副炮实时画面（监控屏）必须在「看舷窗」的余光里。**
> 如果看监控得转头背对战场，注意力来回切换 —— 违反低 APM 设计。

```
俯视（前 = 上）

        ┌────── 舷窗（外景 · 前扇区）──────┐
        │                                    │
        │         ▲ 玩家站位（距窗 1.7 m）     │
        │  [ 控制台 · 4 块副炮实时画面 ]       │   ← 嵌在控制台，正前下方
        │         （下倾 25–35°）             │
        └────────────── 后墙：舱门 ───────────┘
```

| 屏位 | 转头角度 | 用途 | 使用频率 |
|------|---------|------|---------|
| **副炮实时画面（4 块）** | **0°（正前下方）** | 各副炮视角的实时战况（低清低帧 feed） | ⭐ **余光常读** |
| （接管切主视角） | 切换主相机 | **点该路 feed 或按数字键 1–5** 接管，切过去看着打；**ESC 回主控室** | 该面吃紧时主动切 |

- 监控屏距眼 0.9 – 1.2 m，**向下倾斜 25 – 35°**
- 玩家平视舷窗时，用**下视野余光**就能读到其余四面状态
- 4 块画面 = 左右上下四门副炮的实时 feed（SubViewport 渲染到控制台屏幕网格）

⭐ **这是用户那句「监控屏只需要简单看一看」的物理实现** —— 不靠玩家自律去扫视，而是放进余光里。若把监控屏放侧墙，玩家得在「看战场」和「看信息」间反复转头，低 APM 设计立刻崩。

## 五、监控形态（渲染）· 已定

**本作监控 = 主控室常驻 4 路副炮实时画面（SubViewport 渲染）+ 接管时切主视角。**

| 形态 | 做法 | 渲染成本 | 状态 |
|------|------|----------|------|
| **常驻实时画面（主形态）** | 控制台常驻 4 块副炮实时画面，扫视即知哪面有压力 | 4 路低清低帧额外渲染（SubViewport） | **Prototype 实现**（DEC-038） |
| **接管切主视角** | 手动接管时把主相机切到该副炮，精确射击 | 仅相机移动（主视角本就要渲） | Prototype 实现 |
| 2D 雷达总览（可选） | 纯 2D UI 画各面压力概览，作为快速扫读 | 零额外渲染 | 可选，非必需 |

⚠️ **性能是真实开销，必须规划**：4 路常驻 feed = **4 路额外场景渲染**（每路一个 Viewport + Camera）。**这不是「切相机零开销」**——当你要求「在主控室同时看到其他副炮画面」时，那些画面必须常驻渲染（DEC-039）。但通过**低分辨率（320×180 ~ 512×288）+ 低帧率（8–12 fps）**可压到极低：这些画面只用来扫视，不需要高清高帧。现代中端机器上几乎无感。

**渲染实现**（Godot）：每门副炮挂一个 `Camera3D` + 一个 `SubViewport`（低分辨率），其 `ViewportTexture` 贴到控制台对应屏幕网格；主相机照常渲染主视角。4 个 SubViewport 的总开销远低于「六面全息图 + 多路高清渲染」。

**执行顺序**：Prototype 直接做 4 路常驻 feed（低清低帧起步）+ 接管切主视角，验证 P-2 假设（玩家会不会看这些画面来判断）。若低端机实测吃紧，降级手段（按优先级）：① 降 feed 分辨率/帧率 → ② 隐藏无威胁面的 feed（如该面无敌人时不渲染）→ ③ 退回 2D 雷达总览。

> 注：第四节控制台上的 4 块副炮实时画面就是**核心监控回路**；可选 2D 雷达总览只是快速扫读的补充，非必需。

## 六、音频（骨架已搭：⑩，2026-09-10 · DEC-046）

**用户判断：空间音频没那么重要，因为信息都在面前屏幕上。同意。**
（原因在本作尤其硬：DEC-026 只有艏部一面舷窗，其余五面**本来就看不见**，
所以声音要给的从来不是"方向感"，而是"哪一面在出事"。）

- 总线 **4 条**：`Master` → `Music` / `SFX` / `UI`（**DEC-046 决定 1**）。
  比原计划的 3 条多一条 `UI`，理由：界面音需要独立音量、且将来 VO 播报要 duck 的是 SFX 而不是 UI 音。
- ⭐ **比 3D 定位更可靠的是「听觉 HUD」**：不同扇区受击用不同音高。玩家要的是「听得懂是哪一面」，不是「听得出方向」。
  - **已落地**：映射表在 `data/audio.json` 的 `sector_hud` 段（6 扇区各一个 `pitch` + `spatial` 开关）。
    基准取值供参考：前 1.00 / 左 1.15 / 右 0.90 / 上 1.30 / 下 0.65 / 后 0.75 —— **实机听着别扭就改 JSON，不用碰代码**。
  - **防爆限流按「音效 id + 扇区」计窗口**，不按 id 全局计。否则同时被两面打时，
    先到的那个扇区会吃掉限流窗口、把另一面弄成静音 —— 恰好把听觉 HUD 的核心信息盖掉。

**空间音频的正确用法（范围很小）**：

| 场景 | 用不用 3D |
|------|----------|
| **前扇区**战斗（舷窗看得见的部分） | ✅ 用 `AudioStreamPlayer3D`（由 `sector_hud.fore.spatial = true` 打开） |
| 其余五扇区战斗 | ❌ 不用 —— 封闭舰桥内，船体传导声本就不该有清晰方向感 |
| 舰桥内环境音、警报、播报 | ❌ 不用 |

`AudioStreamPlayer3D` 参数（衰减模型 `INVERSE_DISTANCE`、`max_distance` 250 – 400 m、`unit_size` 10 – 15 m）
**已移入 `data/audio.json` 的 `spatial` 段**（2026-09-10，⑩）——
本文档只保留区间，实际取值与全部音效/音量/限流阈值同源，见 `data/audio.json`。

**零素材可用**：`assets/audio/` 为空时，`AudioManager` 按 `audio.json` 每个条目的 `tone` 参数
**现场合成一段占位音**（全内存、不落盘、不需导入）。正式素材放进条目 `path` 指向的位置后自动接管，
配置一个字都不用改。所以白盒阶段不必等美术就能听见反馈。

> ❓ **Q9 仍待决**：是否加第 5 条 `VO` 总线（舰载 AI 播报）？⑩ 未采纳（当前无播报内容，
> 加了就是空转一条总线）。若采纳，同步改 `MODULES.md` 的 AudioManager 描述与 audio.json 的 `buses` 段。

## 八、旋钮表 → `data/presentation.json`

| 字段 | 含义 | 参考区间 |

### 尺度自检（改任何一个尺度参数后，跑一遍这四条）

1. 舷窗视野全角 = `2 · atan(viewport_width / 2 / console_distance)` → 是否还在 100–120°？
2. 威胁窗口 = `(spawn_radius − attack_range) / enemy_speed` → 是否还 ≥ 8 s？
3. 进场可见度 = `enemy_size / spawn_radius` → 1080p 下是否还 ≥ 15 px？（实际 27.9 px 起）
4. 玩家背后有没有 4 m 空间走到后墙？`console_distance + 4.0 ≈ bridge.depth`？

> 这四条自检是「为什么是这些数」的可执行版本。改数值时跑一遍，比凭感觉调快得多。

### 手感的归属边界（⑪ · DEC-047）

`feel` 段的消费者有三个，落在三层，**读同一份 JSON（经 `FeelKit`），但写的东西互不重叠**：

| 谁 | 写什么 | 不碰什么 |
|----|--------|---------|
| `GameFeel`（挂主控室子节点） | `Camera3D.position`（局部偏移）· `Camera3D.fov` | `Player.position` / `rotation` —— 那是 bridge_whitebox 的地盘 |
| `Enemy` / `Turret`（实体自己） | 自己 `material_override.albedo_color` | 相机 |
| `bridge_whitebox` | `Player.position` / `rotation`（接管搬移、feed 布局） | 相机局部偏移与 fov |

**为什么闪白不放 GameFeel**：材质属于实体自己，且实体层不该为了两个颜色常量去读整个呈现层配置 ——
所以 `FeelKit` 提供了不带 autoload 的静态读取（少一个 autoload 就少一个"顺序"坑，见 `godot_pitfalls.md #13`）。

**L3 终局必须让位**：`CollapseSequence` 夺镜期间 `GameFeel` 通过兄弟节点 `is_locked()` 自我静音，
否则「被包围」的镜头会一边环绕一边抖。

## 十、改装过场流程（**已采纳 → DEC-041**；阶段 A 已落地 2026-09-08）

### 意图：把 REFIT 从「一个界面」变成「一个地方」

现状的危机循环是 `战斗 → 黑盒般的 REFIT → 战斗`，装配动作悬空、没有物理锚点。
本提案给循环加一个**家**：每波打完飞去维修站，修船、换炮、再出发。参照物是
**《Hades》的 House of Hades**（每局死亡回家 → 家里推进叙事/强化 → 再出门）：
「回家」本身成为循环的情绪缓冲和世界观载体。

### 流程（李的原始构想，整理后）

| 步 | 演出 | 玩家能做什么 |
|----|------|-------------|
| 1 | 本波清空 → 飞船脱离战区，**飞向维修站过场**（空间站或星球地表均可，动画飞来飞走） | 看过场 / 跳过 |
| 2 | 停靠 → **切维修师镜头**，**用一句话报告战损**（氛围台词，DEC-043 战损 ③ 出口 ——"左舷那门废了"那种，不列数字），并问是否改装 | 听 / 跳过 |
| 3 | 玩家选择改装 → **切到炮塔位置**，浏览可选炮塔类型并选定 | 装配决策（主玩法） |
| 4 | 旧炮塔拆除 → 新炮塔安装，**带换装特效**（消失 / 出现各配效果） | 确认 |

### 行业经验与风险

- **重复观看疲劳**：过场每次危机都放，第二次起就会烦。
  **本作结论（DEC-041）**：**可跳过但不给按钮**。单段 2-3 秒不配拥有 UI 按钮，
  但每波都播 × 一天几十局会累积成十几分钟 → 做成**隐形能力**：
  过场期间任意键 = 立即补完**当前阶段**（不是跳过整个过场）。改装台阶段不吞键。
- **维修站选型**：先按**空间站**做（无重力/大气/地表材质成本）；星球地表版等美术量上来了再议。
- **无经济**：**Q15 已定 → 台词纯氛围**（"这次费了点功夫"），不动 DEC-033。

### 制作路线：分两阶段，**不阻塞在模型上**（与 ⑥ 冻结同一模式）

**阶段 A · 白盒轻量版 —— ✅ 已完成（2026-09-08，`refit_test.tscn` 33/33）**

| 项 | 落地位置 |
|----|---------|
| 黑屏淡入淡出 | `RefitOverlay._fade`（CanvasLayer，层 10） |
| 维修师 2D 对话框（占位头像 + 名字 + 打字机） | `RefitOverlay.show_mechanic` / `type_step` |
| 台词库（纯氛围，按危机数轮换） | `data/refit.json` 的 `mechanic` 段 |
| **真正的换装**（读 `turrets.json` 选型 → 换数值 + 外观） | `TurretSystem.swap_turret()` |
| 换装特效（旧炮缩小消失 / 新炮弹出 / 冲击环） | `TurretSystem._play_retire_fx` / `_play_install_fx` / `_play_shock_ring` |
| 「飞向维修站」降级 | 黑屏 + 一行字（`refit.json` 的 `travel.line`） |
| 阶段机与跳过 | `scripts/systems/refit_sequence.gd` |

**阶段 A 的两个实测教训**（写下来免得阶段 B 重踩）：
1. 换装特效**不能挂在旧炮塔上**（会随 `queue_free` 一起消失），也**不能挂 `get_tree().get_root()`**
   （root 正在 setup 子节点时 `add_child` 直接失败）→ 挂 TurretSystem 自己的常驻 `SwapFXRoot`。
2. 改装台黑幕**必须是 0.55 而不是 1.0**：全黑就看不见换装特效了，
   而「看见旧炮消失 / 新炮弹出」正是无模型阶段唯一的正反馈。面板也因此贴底不居中。

**阶段 B · 3D 演出版（等模型到位，与 ⑥ 监控接真副炮同一批解锁）**

1. 维修站建模入场；飞船沿 `Path3D + PathFollow3D` 飞行曲线（Godot 标准做法），相机脱离玩家控制由 `AnimationPlayer` / Tween 驱动。
2. 维修师角色模型 + 镜头；对话升级为 3D 呈现（台词文本层复用阶段 A 的）。
3. 舱内换炮镜头：真实炮位特写 + 拆装动画。

**技术约束**：
- **不新增全局状态**。过场是 REFIT 的**入场演出**（可跳过），`MENU/REFIT/BATTLE/RESULT` 保持四态；过场期间用 `EventBus` 发 `cutscene_started/ended`，输入层据此屏蔽，别把跳过逻辑散进状态机。
- 时长/跳过参数外置 `data/presentation.json`（新增 `cutscene` 段），不 hardcode。
